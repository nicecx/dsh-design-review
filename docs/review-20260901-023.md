# 20260901-023 队列体验改进：排队替代拒绝 + 可见性 + 归档（多会话并行）

- requestId: 20260901-023
- 类型: design（用户反馈：单槽 skip 导致多会话"被放弃审核"）

## 复用评估

- 本地 CAPABILITY-INDEX：dsh-task-queue 插件自身扩展（queueMode 语义调整）；消费端 cron 不变
- 外部（awesome）：无对应条目；GitHub：无直接同型方案
- 无复用：排队语义/可见性/归档为新逻辑

## 背景与问题（实测）

- 投资会话提审（022）后，再提"仲裁机制设计"被 **queueMode=skip 直接拒绝**（队列已有 pending）→ 会话"放弃审核"
- 单槽串行吞吐 2-3 个/小时；多会话并行时 skip=劝退
- queue.json done 任务不归档（81 个任务中 80 done）→ 观感噪音（29 个 done review 被误读为积压）

## 方案

**核心原则（用户裁定）：入队必审——排队可以等，但任何提审不得被拒绝。** 积压通过告警+扩容解决，不通过拒绝解决。

### 1. queueMode=queue（无上限拒绝，替代 skip 拒绝）
- 入队端（dsh-design-review submit / review_submit.py）：队列已有 queued/processing review 时**一律入队排队**（status=queued，追加队尾）——**永不拒绝**（不设拒绝上限）
- **上限仅作为告警阈值** REV_QUEUE_ALERT=3：queued review ≥3 → 不拒绝，但：①入队返回提示排队位置+预计等待 ②消费端输出告警签名行（monitor 唤醒 agent 处理积压/扩容）
- 消费端不变（单槽出队——一次审一个；吞吐 2-3/h，排队确定性消耗）

### 1b. 积压兜底（防"排队无限长"）
- 积压告警触发后，agent（或 Hermes 守护）介入：评估是否**扩容审核**（如临时并行第二审核槽/加速审核节奏）或**用户知情决策**（等待 vs 紧急插队）
- 绝不静默拒绝；每个入队请求都有确定性的"会被处理"承诺

### 2. 排队可见性（提审返回排队位置）
- submit 返回（及 deliver 通知）带排队信息：`队列位置：第 N 位（前 N-1 个待审，预计等待 ~N×25min）`
- 排队位置 = queued review 中该任务的 index+1

### 3. done 归档
- 消费端完成任务时：`done` 状态任务保留 24h 后由消费端顺带归档到 `queue.archive.jsonl`（append-only），queue.json 仅保留 queued/processing/failed + 24h 内 done
- 归档不丢审计（archive 文件可查）

### 4. 积压告警（015 落地，仅告警不拒绝）
- 消费端扫描时：queued review ≥3 → 输出稳定签名行告警（monitor 门控唤醒 agent 处理积压）
- 优先级不变：reset > approve > review + FIFO + aging

## 接口与兼容性

- queueMode 配置值 'skip' 保留（兼容），新增 'queue'（默认改为 queue + 上限）——cordis.patch.yml 更新 dsh-design-review queueMode=queue
- 消费端任务模型不变（status 字段不变）
- 归档文件新路径（queue.archive.jsonl），不破坏 queue.json 读取

## 安全

- 无新权限；拒绝路径仍 fail-closed；排队上限防无限积压（DoS 防护）

## 测试方案

- T1：队列 1 个 queued → 新提审入队排队（不再拒绝），返回位置 2
- T2：队列 5 个 queued → 新提审**仍入队**（永不拒绝），返回位置 6 + 提示预计等待
- T3：done 任务 24h 后归档（mock 时间）→ queue.json 不含，archive 含
- T4：queued ≥3 → 消费端输出告警签名行（仅告警，不拒绝）
- T5：skip 配置兼容（旧配置行为不变）

## 风险与回滚

- 风险：排队模式队列增长 → 告警触发扩容/人工决策（不拒绝）；回滚：queueMode 改回 skip
